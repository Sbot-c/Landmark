### Pipeline — dependency justification

The diagram (`pipeline.png` / editable `pipeline.dot`) shows the pipeline **as implemented** in the notebook. Solid boxes were built and executed; dashed boxes are proposed (Key Ring) or simulated (ε-greedy sandbox). Each dependency is justified below in two or three sentences.

**1. Raw files → audit & validation → cleaning.** No feature can be trusted until keys, duplicates, ID formats, dates and amounts have been checked, so the audit is fixed as Stage 0. Cleaning deletes nothing (no duplicates or invalid rows exist); it flags pre-signup transactions and partial periods instead, which keeps recorded revenue reconciled to the source files to the dirham.

**2. Cleaning → unified customer view (as-of 2026-10-01).** Aggregating to one row per Shukran member only *after* validation prevents a join from multiplying rows and inflating revenue (checked by assertions). The view is built by a single function that can be re-run at any reference date, which is what makes the temporal churn and CLV designs possible later.

**3. Viva branch → Group financials only (never the customer view).** Viva uses a separate identity system and the attempted join returns zero matches, so its revenue enters Group-level analysis and the eight-banner ranking but never a member's profile. Forcing a join (e.g. stripping ID prefixes) was rejected because it would manufacture links between unrelated people; the Key Ring proposal is the governed alternative.

**4. Unified view → standardisation → (raw features or PCA) → clustering → named segments.** Features are standardised so that no unit dominates distance. PCA is fitted as a *candidate* representation (it decorrelates the seven compositional banner shares and gives the 2-D map); both representations, and both Euclidean K-means and Manhattan K-medoids, are clustered and scored on a like-for-like basis — every partition's silhouette is measured in the same raw space under both metrics — and the deployed segmentation uses whichever separates members better, with ties going to the simpler raw pipeline. The selected representation and algorithm are read from `cluster_choice.json` and shown on the diagram. Segmenting on transactions directly was rejected because it groups baskets, not customers. A second, behaviour-only *shopping-style* clustering (frequency, spend, ticket size, discount use, banner count — no banner shares) is run from the same view as a descriptive cross-check; it never feeds a model.

**5. Segments are *not* inputs to churn or routing models.** The segments were built from recency (the churn label's own window) and from home/fashion banner shares (the routing labels), so feeding them into those models would leak the answer. Segments are therefore applied *after* modelling — for per-segment bundles, value-weighted retention priorities and profiling — which is a deliberate departure from the "segment first, then model within segments" option.

**6. Unified view → temporal and non-target views → leakage audits → model laboratory.** Churn features are frozen 90 days before the as-of date because the supplied churn flag is effectively "no purchase in the last 90 days"; routing features are recomputed on non-home / non-fashion transactions to remove direct and denominator-based leakage. The audits run first and quantify what each forbidden design would have scored, so the honest scores are interpreted against the leaky ones.

**7. Model laboratory → churn threshold & cost → deployment scores.** A threshold can only be chosen once probabilities have been validated, so threshold tuning (TunedThresholdClassifierCV with a 5:1 relative cost, plus a lower threshold for high-value members) follows model selection and uses training-fold predictions only. The test set is used once, after both decisions are locked.

**8. Unified view → CLV regression → value tiers → value-weighted churn.** CLV supplies the value axis that turns a churn list into a prioritised retention list (risk × value), answering the Case Study's question of whether churn and CLV should feed each other. The historical model is accompanied by a circularity audit, and a next-180-day model built at an earlier cutoff provides the forward-looking value. Several loss designs (squared error, log target, Poisson, and a two-part *will they buy × how much* model) compete under the same cross-validation; a BG/NBD × Gamma-Gamma probabilistic model is the external benchmark, and conformalised quantile regression attaches an 80% range to each forward prediction.

**9. All models → bias–variance diagnosis.** Diagnostics come last among the modelling steps because they compare every fitted family under the same protocol (train vs CV vs test, learning and validation curves, bootstrap decomposition). This is where the variance-reducing effect of bagging and the bias-reducing effect of boosting are measured rather than assumed.

**10. Unified view + segments → Apriori → bundles → ε-greedy sandbox.** Member-level banner baskets exist only because Shukran gives one ID across seven banners, so basket analysis depends on the unified view; mining within each segment shows whether an affinity is Group-wide or segment-specific. Bundles are sized by eligible members (shops A, not yet B) with their risk and value, and the ε-greedy sandbox simulates how those offers would be tested live — it is not evidence of uplift.

**11. Segments, risk, routing → Shukran analytics, discount dependency, migration.** These business analyses combine outputs of several upstream models (segments, forward churn risk, routing probabilities), so they must follow them. Migration candidates use out-of-fold routing probabilities so that no member is scored by a model trained on them.

**12. Models → validation layer.** After each model is selected, it is checked before its outputs are used: an out-of-time test (does the churn relationship hold in a period the model never saw?), a paired ablation of the one feature tied to the data window, probability calibration, bootstrap confidence intervals for every test score, and a scoring guard that clips features to their training range before forward scoring. These checks come after selection — never before — so they cannot influence which model is chosen; they decide how much weight the outputs deserve. Apriori rules get the same treatment (activity- and household-adjusted lift, customer-month baskets) before they rank bundles.

**13. Everything → dashboard.** The dashboard reads the saved artifacts and never retrains, so every figure it shows is identical to the notebook's. Interactive controls only re-filter data or recompute clearly labelled scenarios (margins, cost ratios, discount depth, bandit simulation).
